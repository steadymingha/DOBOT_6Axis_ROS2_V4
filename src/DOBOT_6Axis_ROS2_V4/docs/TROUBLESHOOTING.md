# 트러블슈팅 정리 (재발 대비용)

CR7 + MPO-700 픽앤플레이스 프로젝트에서 실제로 겪은 것 중, **다시 겪을 확률이 높은 것**만 추림.
증상 → 원인 → 대응 순. 수치·세부 절차는 원본 문서 참조.

---

## A. 조용히 실패하는 것

에러 없이 잘못된 상태로 진행되는 부류. 가장 비쌌고, 새 코드 넣을 때마다 같은 기준으로 점검함.

- **URDF vs 컨트롤러 관절 부호 불일치** — URDF가 J1·J5·J6 회전축을 컨트롤러와 반대로 정의함. 그대로 두면 pinocchio 스택(IK/CBiRRT/충돌검사)이 팔을 거울 반전 자세로 몲. 시뮬은 URDF가 곧 로봇이라 자기일관적이어서 원리적으로 안 드러남. ROS 경계(`node.py`)에서만 부호 반전하고 `CR7_REAL_ROBOT=1`로 옵트인함. 조그는 URDF를 안 거쳐 무관.
  → 기동 시 모델 FK와 로봇 `tool_vector` 대조(수 mm 이내)로 켜졌는지 확인함.

- **`depth_units` 오염** — D405의 depth 스케일은 카메라 펌웨어에 남는 장치 옵션이라 다른 프로세스가 바꿔놓으면 그대로 남음. 0.001로 오염돼 거리가 10배 틀어져 있었음. **반드시 `pipeline.start()` 전에** 설정함. 스트리밍 시작 후 바꾸면 보고값만 바뀌고 실제 양자화는 그대로라 되읽기 검증까지 통과함.

- **`execute_path`가 실패해도 True 반환** — `_wait_settled` 타임아웃에도 True. 시뮬에선 맞지만 실물에서는 **보호정지가 성공과 똑같이 보임**(mode 11 트립이 완료 사이클로 기록된 사례). 매 구간을 30004 상태와 대조하는 `arrived()` 게이트를 둠.

- **`update_shelf_collision()`이 TF 실패를 경고로만 넘김** — False를 반환하고 진행하면 선반 판 팬텀이 park된 채 남아 **충돌모델이 꺼진 상태로 시퀀스가 돎**. 호출부에서 반환값 검사해 중단(fail-closed)함.

- **park = 충돌모델 꺼짐** — 팬텀은 제거하지 않고 `z=-100`으로 park하는 구조. 등록 로그가 정상으로 찍혀도 park된 채면 없는 것과 같음. 배치 함수 반환값을 검사하고, 기동 로그의 `[collision] added N ...` 줄이 **실제로 찍히는지**로 확인함.

- **서비스/액션 반환값 버리기** — `attach_box()` 실패를 무시했더니 "운반 중 낙하"라는 엉뚱한 증상으로 둔갑함. 실패 시 그리퍼 열고 사이클 중단(조용한 실패 금지).

- **액션 서버 중복 실행** — 같은 `follow_joint_trajectory`에 서버가 둘 붙으면 goal 하나를 양쪽이 받아 각자 ServoJ를 쏨. 팔이 튀고 충돌 트립. ROS 2가 안 막아줌. `ros2 action info -t` 또는 `--status`의 `UP x2`로 확인함. 조그 버그처럼 보이지만 아님.

- **런타임 자유도** — `rotate_j6`가 충돌 시 조용히 부호를 뒤집으면 pregrasp에 구운 측면 오프셋이 반전돼 든 박스가 엉뚱한 데로 감. 검증한 값을 pin하고 그것만 실행함(아래 C 참조).

## B. 진단 순서

증상별로 "어디부터 보나"를 고정해 둔 것. 코드 요소를 먼저 의심하다 헤맨 사례가 반복됨.

- **CBiRRT carry가 멈춤** → 추측 말고 **per-joint gap 로그부터** 찍음.
  - J1만 큼 → 배치/azimuth 문제
  - J3·J5 동시에 큼 → 엘보+리스트 브랜치 불일치 (pick을 place와 같은 IK family로 잡게 함)
  - J6만 큼 → yaw 와인딩 (goal의 yaw를 자유롭게)
  - ±180° 가까운 관절이 없으면 정상.

- **RViz에 아무것도 안 보임 (Status는 OK)** → 1순위 용의자는 **Fixed Frame**. 데이터 프레임과 안 맞거나 존재하지 않는 프레임이면 모든 디스플레이를 조용히 드롭함. 색·마커 타입·rgb baking 같은 코드 요소를 먼저 의심하지 않음.

- **vision 값이 틀림** → 단계별로 분리 계측함: 코너 reproj(카메라 TF·K·검출) / depth→월드(정합) / 태그 중심 / 최종 pose. 어느 단계에서 오차가 들어오는지 확정한 뒤 고침. 앞 단계가 다 무죄인데 최종만 널뛰면 원인은 **회전**임.

- **오차가 있는데 spread가 0** → 노이즈나 조건수 문제가 아니라 **상수 캘리브 바이어스**. 뷰를 늘리거나 태그를 키워도 안 없어짐. 상쇄 구조(anchor)로 처리함.

- **안 닿았는데 물체가 튕김** → Gazebo `View → Collisions`로 충돌체와 비주얼을 대조함. 오목한(C/L자) 형상을 메시 AABB로 만들면 빈 공간이 솔리드가 됨.

- **"모델은 되는데 시뮬은 안 됨"** → 로봇 description 사본이 여러 개(Gazebo 스폰 / move_group / IK·서보 / 플래닝) 돌아다녀 어긋난 것부터 의심함.

## C. 계획·충돌모델 원칙

코드 고칠 때마다 걸리는 것들. 새 시퀀스/프리미티브를 넣을 때 이 기준으로 검토함.

- **충돌모델은 항상 실물을 bound함.** 관절 있는 부품은 **가장 크게 열리는 상태**로 freeze함(neutral로 두면 실제 조가 모델 밖으로 30 mm 나가 planner가 통과시킨 경로가 물체를 침). 명령값이 모델을 넘을 수 없게 상수를 묶어둠.

- **회피 팬텀은 절대 축소하지 않음.** 실물에서는 오히려 **팽창**시킴(비전 검출 + hand-eye 잔차 + FK + 레이아웃 공차의 합). 팽창량은 감이 아니라 오차 예산으로 잡고, 물체 간 빈틈의 절반을 넘으면 플래너가 아니라 측정을 개선함.

- **역재생 보장은 동일 관절경로에만 성립함.** J6 트위스트 같은 오프셋이 얹히면 같은 TCP 선이어도 스윕 볼륨이 다른 **새 경로**이므로 재검증 대상임.

- **충돌검사는 등록된 페어만 봄.** 페어 없는 팬텀은 투명함. 특정 문맥에서 false-positive가 나면 지우지 말고 **문맥별 토글**로 둠(상시 ON은 오검출, 상시 OFF는 장님).

- **검증과 실행 사이에 런타임 자유도를 남기지 않음.** 실행 시점에 방향·부호·IK 브랜치를 고르는 프리미티브는 pre-flight를 무효화함. 검증한 선택을 pin하고 그것만 실행함.

- **모든 검사를 첫 모션 이전으로 옮김.** 최악의 결과가 "무동작 + 명확한 로그"가 되게 함. 중간에 멈춰 박스를 문 채 스트랜딩되는 상황을 없앰. 실패 시 이미 실행한 경로의 역재생으로 빠져나옴.

- **CBiRRT는 "수직"이 아니라 출발 자세의 툴 기울기를 유지함.** 기울어진 자세에서 교시하면 그 기울기를 경로 내내 안고 가고, 목표가 그 다양체 밖이면 마지막에 계획되지 않은 한 걸음이 튐(착지 오차의 정체). 교시는 자세를 수직으로 스냅(`--level`)해서 함. 툴축 둘레 회전(J6)은 구속 안에서 자유라 문제없음.

- **IK 브랜치는 family로 묶어 생각함.** 높은 곳은 엘보-업, 낮고 가까운 곳은 엘보-다운을 강제하므로 pick과 place가 다른 family면 제약 매니폴드 위에서 이을 수 없음. pick을 place의 family로 잡게 함. 호환 브랜치가 관절제한(특히 J4 음수)에 막혀 있으면 충돌프리인 한 제한을 풂.

- **상수는 좌표가 아니라 "정도"로 정의하고 파생값은 코드에서 유도함.** 좌표를 직접 넣으면 하나 바꿀 때 다른 게 따라 바뀜(삽입 높이를 건드려 특이점을 만든 사례). 레이아웃 값은 한 곳(`geometry.py` / env json)에만 두고 world와 코드가 따로 놀지 않게 함.

- **접촉 감지·표면 교시는 충돌 모델 자체를 자로 씀.** 측정과 강제를 같은 모델로 하므로 자기일관적이지만, **잴 때의 손목 자세를 작업할 때와 같게** 둬야 팬텀 그리퍼와 실물 툴의 치수 차이가 상수로 상쇄됨.

- **모델에 없는 것을 알고 있음** — 매거진, 집는 박스, 작업 대상물, 방(테이블·벽·트롤리)은 어느 모델에도 없음. 수직 하강은 접촉 정지가, 방은 표면 교시가 담당함. 교시하지 않으면 팔은 테이블이 없다고 믿고 계획함.

## D. 실물 인프라 (Jetson / 네트워크 / 실행 환경)

한 번 겪으면 며칠 날리는 환경 문제.

- **첫 goal이 20초 타임아웃** — 3층으로 겹쳐 있었음. 단서는 **"이미 붙어 있던 노드는 멀쩡한데 새로 띄운 노드만 실패"**.
  1. 커널 UDP 버퍼 기본값(208 KB)으로는 대형 참가자의 DDS discovery 버스트가 드롭됨 → `net.core.rmem_max` 확대 후 **sim 재기동**(기존 소켓은 작은 버퍼 유지)
  2. `ROS_LOCALHOST_ONLY=1` 고정 — 사내망으로 discovery가 나가는 부하를 끊음
  3. Fast DDS가 localhost 앞쪽 4개 참가자 슬롯만 두드림 → probe 범위를 넓힌 프로파일 로드
  → 셋 다 **모든 터미널이 같은 값**이어야 함.

- **python 혼용 segfault** — `.venv`(numpy 2.x)로 시퀀스를 돌리면 `/opt/ros`의 pinocchio(numpy 1.x 빌드)와 충돌해 segfault. 시퀀스·vision 노드는 system python3, pinocchio 도구는 `.venv`로 구분해 씀. conda가 활성이면 PATH에서 벗김.

- **Docker에서 `/dev` 접근** — `-v /dev:/dev`만으론 안 됨. device cgroup이 major 번호별로 막으므로 video4linux/USB/input을 각각 허용해야 실제로 열림. 안 하면 파일은 보이는데 `open()`이 `Operation not permitted`로 막힘.

- **`install/` 사본이 실행됨** — 패키지에 설치되는 파일(action server, config 등)은 소스만 고치면 반영 안 됨. `colcon build --packages-select` + 해당 터미널 재시작 필요. `tools/*.py`는 소스 직접 실행이라 불필요.

- **카메라는 한 프로세스만 엶** — `realsense2_camera` 노드나 다른 하네스가 떠 있으면 러너가 `Device or resource busy`로 죽음. hand-eye 캘리브 끝나면 반드시 내림. sim/실물 드라이버를 동시에 띄우면 같은 토픽에 발행자가 둘 생겨 입력이 섞임.

- **D405 하드웨어 불안정** — USB 자동 서스펜드(`power/control=auto`)로 하루에 여러 번 얼어붙음(프로세스는 살아 있는데 프레임 정지). 물리적 재연결로만 완전 복구됨. 측정 중 재발하면 그 회차는 버림.

- **로봇 소켓 점유** — 29999 대시보드는 단일 클라이언트라 브링업이 점유함(설정은 서비스 경유). 30004 실시간 피드는 다중 읽기 허용이라 브링업과 동시에 열어도 됨.

- **컨트롤러 명령 함정** — `MoveJog`의 Cartesian 축은 `coordtype`을 같이 안 보내면 항상 거부됨(관절 축은 불필요해서 "JOINT는 되는데 TCP만 무반응"으로 보임). `ServoJ`는 고정 주기 스트리밍용이라 궤적 타이밍을 무시하고 고정 간격으로 쏘면 저크·추종오차가 남.

- **`rclpy.init()`이 SIGINT를 삼킴** — Ctrl+C가 `KeyboardInterrupt`로 안 올라와 `finally`의 로봇 정지 코드가 실행 안 됨. 시그널 핸들러를 끄고 직접 처리함.

- **오버레이된 패키지** — 워크스페이스에 패치본이 apt 버전을 덮어쓰고 있음(디렉터리명만 다르고 패키지명 동일). 시뮬이 갑자기 안 뜨면 어느 워크스페이스를 source 했는지부터 봄.

## E. 미해결 / 알고 있어야 할 부채

A~D에서 "이렇게 막았음"이라고 적힌 것 중, **아직 안 막힌 경로**와 임시로 덮어둔 것들. 실물 작업 전에 확인함.

- **`main.py`에 `CR7_REAL_ROBOT=1`이 없음** — A의 관절 부호 반전은 `test/cbirrt_p1p2_test.py`가 import 시점에 스스로 켜지만, `main.py`는 안 켬. 실물에서 그대로 돌리면 J1·J5·J6가 거울 반전됨. 환경변수 선언보다 **기동 시 모델 FK vs 로봇 `tool_vector` 대조**(실측 잔차 ~2.5 mm)로 막는 쪽을 제안해 뒀으나 미적용.

- **`.venv`의 cv2가 MagicMock 더미** — pinocchio가 있는 venv는 numpy 2.x, 컨테이너 cv2는 numpy 1.x 빌드라 `import cv2` 자체가 깨짐. 지금은 `handeye_calib`의 순수 numpy 함수만 쓰므로 무해하지만, **이 프로세스에 cv2를 호출하는 코드가 들어오면 반환값이 MagicMock이 되어 조용히 오동작함**. 항구 해결은 `handeye_calib.py`에서 순수 수학부를 별 모듈로 분리하는 것.

- **실물 그리퍼 액션 서버가 없음** — 코드는 `/gripper_controller/follow_joint_trajectory`를 쓰는데 실물에는 그 서버를 여는 주체가 없음(action server는 group controller만 엶). 현재는 5초 타임아웃 후 실패하고 더미로 우회 중. 누가 열지 미정.

- **`HOVER_CLEARANCE_M` 값 미확정** — 0.10 / 0.08 중 어느 것이 맞는지 정해지지 않음(파일 덮어쓰기로 값이 섞임). 조가 플랜지 아래로 70 mm 내려오므로 0.10이면 조 끝 30 mm, 0.08이면 10 mm 여유.

- **매거진 yaw가 상수로 안 들어감** — 실측 −4° 정도인데 매번 CLI로 주고 있음. 상수화할 때 **안쪽 벡터·조 오프셋·J6를 한꺼번에** 회전시켜야 함(J6만 맞추면 안쪽 오프셋이 도당 몇 mm씩 틀어짐).

- **매거진이 여러 개일 때 선택 규칙이 없음** — 게이트는 통과한 검출 중 `score` 최대를 고름("한 대씩 온다"는 전제). 선반에 여러 개가 보이면 매 회차 어느 것이 뽑힐지 사실상 임의. 게이트는 수정 금지이므로 선택은 호출부에서 함.

- **`VISION_WORK_BOX`가 잠정값** — 넉넉히 잡아둔 상태. 배치가 굳으면 실측 크기로 좁힘. 반대로 AMR이 매거진을 싣고 들어오기 시작하면(정차 오차 + 적재 변동) 넓혀야 함.

- **팬텀 팽창 3 mm는 값이 아니라 정책** — 실물 파지 편차를 재측정하기 전까지 유지함. 실제 파지(무게·미끄러짐 포함)로 검증한 값이 아님.

- **더미로 통과한 구간은 실물 실패 모드를 안 겪은 것** — 특히 그리퍼. 하중·미끄러짐·파지 편차가 전부 빠진 상태의 carry 검증이므로, 실물 파지 후 충돌 마진을 재검증함.
