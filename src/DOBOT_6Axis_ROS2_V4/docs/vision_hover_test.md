# 비전 호버 + J6 정렬 — 사용법과 설계

2026-08-11. 매거진을 **비전으로 찾아** 그 상면 중심 위 10 cm 에 **플랜지**를 세우고,
J6 를 ±90° 돌려 파지 방향을 맞추는 데까지. **하강 없음.**

이 시험이 곧 **절대 편향 측정**이다. `VISION_CHAIN_VERIFICATION.md` 가 잰 것은
재현성이었다 — 같은 점을 여러 자세에서 봐도 P_base 가 흩어지지 않는다(p95 1.37 mm).
그것은 "사슬이 자기 자신과 일치하는가"이지 "그 점이 매거진이 실제로 있는 자리인가"가
아니다. 후자는 팔을 실제로 그 위에 세워 **줄자로 재야** 숫자가 된다.

먼저 읽을 것: `real_robot_joint_convention.md`(§9.1 프레임), `real_robot_p1p2_test.md`
(§6 안전 게이트), `VISION_CHAIN_VERIFICATION.md`(게이트·변환 사슬).

| 경로 | 역할 |
|---|---|
| `test/vision_target.py` | 비전 획득 + 좌표/IK 계산 전담. 로봇에 명령하지 않는다 |
| `test/cbirrt_p1p2_test.py --vision` | 이동 시퀀스. 기존 approach/settled/안전 게이트를 그대로 재사용 |
| `test/points.json` 의 `obs` | 관측 자세 (교시값) |
| `test/vision_hover_<ts>.json` | 실행 기록 + 사람 실측값 |

## 1. 한 번 실행이 하는 일

```
1. obs 접근            CBiRRT (구속 유지). free RRT 폴백 안 함 — §4
2. 정지 확인
3. 비전 스냅샷         러너 MAGAZINE, 게이트 통과 10프레임 평균
   -> P_base           tool_to_T(tool_vector) @ X @ xyz_cam   (vision_bridge 그대로)
   -> hover            P_base + 안쪽 + [0, 0, 높이/2 + 여유]
   -> q                플랜지 원점 = hover, 툴 수직 아래 (IK)
4. --run 이 아니면 여기서 끝 (계획·목표만 출력)
5. hover 접근          CBiRRT
6. 정지 확인
7. J6 ± J6_ROT_DEG     2점 궤적. 한계를 넘으면 반대 부호를 제안하고 중단(자동 반전 없음)
8. 정지 확인 -> 도착 보고 + 사람 실측 입력 -> json 저장
9. 끝. 원위치 복귀 없음. 러너 IDLE 복귀
```

p2·운반·하강·home 복귀는 이 모드에 **없다.** 하강은 매거진이 충돌 모델에 없는 상태에서
할 일이 아니라 별도 단계로 미뤄져 있다.

## 2. 실행

```bash
T=~/dobot_ws/src/DOBOT_6Axis_ROS2_V4/test/run.sh
P='docker exec -it ros2_dobot bash -lc "source /opt/ros/humble/setup.bash;
   source /root/dobot_ws/install/setup.bash; export DOBOT_TYPE=cr7;
   cd /root/dobot_ws/src/DOBOT_6Axis_ROS2_V4;
   /root/dobot_ws/.venv/bin/python3 -u test/vision_target.py'   # 아래 도구용

# 0) 프레임 자가시험 — 로봇도 러너도 필요 없다
$P                       # 인자 없이 = selftest
# 1) obs 찾기 — 게이트가 통과하는 자세를 조그로 찾는다 (읽기 전용)
$P --probe               # valid/sd/z 와 "스냅샷 #N" 실시간
$P --tilt                # 툴 기울기 실시간 (§4 에서 왜 필요한지)
# 2) 교시 — 로봇을 읽기만 한다
$T --teach obs --level   # ★ --level 필수 (§4)
# 3) 계획만
$T --vision
# 4) 실행 (E-stop 대기, 드래그 모드 해제 필요)
$T --vision --run --speed-factor 20 --speed 0.15
$T --vision --run --j6-deg -90        # 파지 방향 반대
```

`--speed-factor` 는 **종료 후에도 컨트롤러에 남는다.**

## 3. 방어 층 — 무엇이 무엇을 막는가

층마다 보는 것이 다르다. 위층이 통과했다고 아래층이 필요 없어지지 않는다.

```
게이트 valid/sd/z    "이 depth 를 믿을 수 있나"          센서 품질
FK vs tool_vector    "모델과 로봇이 같은 프레임인가"      부호 규약·프레임
VISION_WORK_BOX      "나온 답이 상식적인 자리인가"        사슬 전체의 결과
MAX_MOVE_M           "여기서 거기까지 갈 일인가"          이동량
IK 되돌림 + 충돌검사 "그 자세가 실제로 가능한가"          기구학·충돌
```

### 3-1. 게이트 (`vision_bridge/gate.py`, 우리가 만들지 않은 층은 아니지만 수정 금지)

`valid_pct`(ROI 유효 depth 픽셀 비율)와 `sd_cm`(전면 평면 피팅 잔차)이 핵심이다.
**Z 는 그 평면 피팅에서 직접 나온다** — 평면이 흔들리면 Z 가 그만큼 틀어지고,
그 오차는 P_base 로 그대로 넘어간다. `sd 0.25 cm = 2.5 mm` 이고 우리가 재려는 편향이
mm 단위라 문턱이 거기 있다.

탐지 성공(`score 0.97`)은 **화면 어디에 있는지**만 말한다. 거리가 믿을 만한지는
말해주지 않는다. 둘은 다른 질문이고 게이트는 두 번째만 본다.

### 3-2. `VISION_WORK_BOX` — 어떤 상황에서 작동하나 ★

**탐지도 게이트도 다 통과했는데 결과 좌표만 틀린** 경우를 막는 마지막 울타리다.

| 상황 | 탐지·게이트 | WORK_BOX |
|---|---|---|
| **옆 매거진을 봤다** (실측: `side_solid` 가 z=0.31~0.52 m 에 같이 잡힌다). 둘 다 게이트를 통과하면 score 높은 쪽이 뽑힌다 | 전부 통과 | ✓ 목표점이 딴 데라 상자 밖 |
| **hand-eye 가 안 맞다** — 카메라가 떨어져 다시 붙였는데 캘리브를 안 했을 때. `X` 만 틀리면 P_base 가 조용히 몇 cm 밀린다 | 전부 통과 (valid 87%, sd 0.21 그대로) | ✓ |
| **곱 순서·30 mm 환산 회귀** — 누가 코드를 고쳐 프레임이 뒤집히면 수십 cm 튄다 | 전부 통과 | ✓ |
| **팔이 움직이는 중 프레임이 어긋남** | 통과 가능 | ✓ (1차 방어는 정지 판정) |
| **매거진을 실제로 옮겼다** | 정상 | ✓ "다시 재라"고 멈춤 |

`sd 0.21` 은 depth 가 깨끗하다고만 말한다. **그 깨끗한 점이 매거진의 점인지 옆 상자의
점인지, 변환이 맞는지는 아무것도 말해주지 않는다.** WORK_BOX 는 원인을 몰라도 결과가
이상하면 선다.

**작동 시점**: hover 계산 직후, **IK 를 풀기 전, 로봇에 아무것도 보내기 전.** 걸리면
이동 없이 끝나고 그때까지의 값(xyz_cam, P_base, hover, 스냅샷 상세)을 전부 출력한다.

**대가**: 좁게 잡을수록 정상 변동에도 걸린다. 현재 ±5 cm 는 매거진을 고정해 두고
반복 측정하는 이 단계용이다. AMR 이 매거진을 싣고 들어오기 시작하면(정차 오차 ±2 cm +
적재 위치 변동) 넓혀야 한다.

### 3-3. FK vs `tool_vector`

모델이 계산한 플랜지 위치(base_link)와 로봇이 스스로 보고하는 `tool_vector` 를 매번
대조한다. 실측 **2.7 mm** (공칭 URDF 잔차 1.4 mm 수준). 10 mm 를 넘으면 관절 부호
규약이 꺼졌거나 프레임이 바뀐 것이므로 좌표를 믿을 수 없다 — 중단한다.

## 4. 왜 CBiRRT 전용인가 ★

`approach()` 는 출발과 목표의 툴 자세가 `--tilt-tol` 보다 벌어지면 **구속 없는 관절공간
RRT 로 폴백**한다. `--vision` 에서는 그 폴백을 **쓰지 않는다.** 공장 시퀀스가 매거진까지
CBiRRT 로 preflight 를 돌고, 잡은 뒤에는 **IK 재풀이 없이 갔던 경로를 그대로 녹화해
역재생**하기 때문이다. 구속을 버려야만 존재하는 경로는 그 보장을 실어 나를 수 없다.
그래서 `carry()`(엄격 CBiRRT)로 가고, 안 되면 **폴백 대신 거부**한다.

### 4-1. 그래서 obs 는 `--level` 로 교시해야 한다

CBiRRT 의 구속은 **출발 자세의 툴 기울기**를 붙든다. 툴 축 둘레 회전(yaw)은 자유지만
**기울기 자체는 바꿀 수 없다** — 그것이 구속이 금지하는 동작이다. hover 는 정의상
수직이므로, obs 가 기울어 있으면 obs→hover 에 tilt-held 경로가 **존재하지 않는다.**

```
같은 4.5° 라도:
  J6(툴축 둘레) 회전   -> 통과. 그래서 hover 에서 J6 ±90° 를 걱정 없이 돌린다
  손목 기울기 변화     -> 불가능. 구속과 정면으로 모순
```

`--level` 은 팔을 움직이지 않고 **저장된 관절각만** 수직으로 스냅한다(TCP 는 유지).
그러면 실제 팔과 저장값이 그 기울기만큼 벌어지므로, **첫 실행 전에 팔의 툴을 실제로
수직에 맞춰야** 한다. 안 맞추면 obs 로 들어가는 첫 걸음에서

```
[goto obs] taught goal is 0.047 rad off the tilt manifold ... Refusing.
```

가 나온다. 위치는 맞출 필요 없다 — **기울기만** 0 에 가까우면 목표가 같은 다양체에
놓인다. `test/vision_target.py --tilt` 가 그 숫자를 실시간으로 보여준다(로봇의
`tool_vector` 만 읽으므로 모델도 부호 규약도 타지 않는다). 0.5° 아래면 충분하다.
한 번 hover(수직)에서 끝나고 나면 그 뒤 실행은 이 문제가 없다.

## 5. 상수 (`test/vision_target.py` 상단)

| 상수 | 값 | 근거 |
|---|---|---|
| `MAGAZINE_HEIGHT_M` | 0.14 | 비전 점은 전면 **중심**이라 상면까지 +높이/2 |
| `HOVER_CLEARANCE_M` | 0.10 | 이 시험의 측정 대상 자체 (줄자로 100 mm 확인) |
| `MAGAZINE_INWARD_M` | 0.0 | 전면 법선 안쪽으로 깊이/2. **깊이 실측 전이라 자리만.** 추정 금지 |
| `INWARD_AXIS` | `"+x"` | 그 안쪽 방향이 base 의 어느 축인지 **사람이 지정**. 자동 추정 금지 |
| `VISION_WORK_BOX` | 실측 hover ±5 cm | §3-2 |
| `MAX_MOVE_M` | 0.40 | 현재 플랜지 → hover |
| `J6_ROT_DEG` | 90 | `--j6-deg` 로 덮어씀 |

**플랜지 기준이다.** `TCP_OFFSET_M`(팬텀 그리퍼 120 mm)은 실물에 없으므로 목표 기준으로
쓰지 않는다 — IK 입력에서 더해 넣어 모델 내부에서 상쇄시킨다. 충돌 모델의 팬텀 그리퍼는
hover 아래로 40 mm 쯤 드리우지만 매거진이 어느 충돌 모델에도 없어 계획에 영향이 없고,
물리적으로도 플랜지에는 카메라 홀더뿐이라 100 mm 여유 안에서 닿는 것이 없다.

## 6. 실측 부호 규약

`vision_hover_<ts>.json` 의 `measured_convention` 에 그대로 저장된다. 부호 기준이 없는
숫자는 평균 낼 수 없다.

```
frame       base_link  (펜던트 GetPose(user=0, tool=0) 와 같은 축)
definition  플랜지 중심 - 매거진 상면 중심
dx_mm       base +x 방향 편차가 양수
dy_mm       base +y 방향 편차가 양수
height_mm   플랜지에서 상면까지 수직 거리, 항상 양수 (기대 HOVER_CLEARANCE_M)
```

3~5 회 반복한 평균이 보정 상수 후보다. 한 번의 값은 정차·조명·자세 우연이 섞여 있다.

## 7. 함정

- **러너는 10초간 커맨드가 없으면 스스로 IDLE 로 떨어진다.** IDLE 에서는 탐지를 하지
  않으므로 `detections` 가 빈다. 획득 경로와 `--probe` 둘 다 5초 주기로 ping 한다.
  이걸 빠뜨렸을 때 "정지 상태인데 갑자기 검출이 끊긴다"로 보였다 — 탐지 문제가 아니었다.
- **카메라는 한 프로세스만 연다.** hand-eye 캘리브의 `realsense2_camera` 노드가 떠 있으면
  러너가 `Device or resource busy` 로 죽는다. 캘리브를 끝냈으면 그 노드를 내릴 것.
- **`.venv` 의 cv2 는 더미다.** `VISION_CHAIN_VERIFICATION.md` §6-8 (부채).
- **첫 다리의 drift** — §4-1.
- 게이트가 `sd` 로 계속 떨어지면 거리보다 **각도·조명**을 볼 것. 실측: 24 cm 에서
  sd 0.27(탈락), 19 cm 에서 0.21(통과). 검증 세션 기준은 sd 0.21 / valid 90%.

## 8. 복귀 지점 — obs (2026-08-11 07:54:38 교시)

hover 로 못 갔거나 중간에 멈췄을 때 **되돌아와서 다시 시도하는 자리**다. 툴이 정확히
수직이라 여기서 출발하면 CBiRRT 가 바로 풀린다(§4-1). `test/points.json` 의 `obs` 가
곧 이 값이고, 아래는 사람이 펜던트로도 넣을 수 있게 적어둔 것이다.

```
컨트롤러 / 펜던트 (GetAngle)   +266.499  +31.437 -107.958  -13.479  +90.000   +1.012
URDF / points.json / 모델      -266.499  +31.437 -107.958  -13.479  -90.000   -1.012
                               ↑ J1·J5·J6 부호 반전 (real_robot_joint_convention.md §5)

플랜지 GetPose(user=0, tool=0)  x=-151.39  y=-208.87  z=+434.94 mm
                               rx=-179.65  ry=+0.21  rz=+175.81 deg
툴 기울기 (로봇 보고)           0.41 deg   collision_free=True
```

**갱신 이력**: 첫 obs(06:09:26, 컨트롤러 `+266.818 +24.557 -108.000 -6.562 +90.000 +1.011`,
플랜지 y=-256.7 z=+419.6)는 작업거리 0.19 m 기준으로 잡았는데, 반복 측정 중 매거진이
카메라 쪽으로 34 mm 밀려(0.188 → 0.154 m) 대상 아랫변이 화면 밖으로 나가 게이트가
`edge` 로 막혔다. 팔을 뒤로 물려 작업거리를 되찾은 자리를 새 obs 로 교시했다.
**obs 를 옮기면 그 전 회차들과는 조건이 달라진다 -- 실측 평균을 낼 때 섞지 말 것.**

**복귀 방법**: `--vision` 자체는 원위치 자동 복귀를 하지 않는다(설계). 대신 되돌아오는
명령이 따로 있다 -- 반복 측정에서 매번 손으로 돌아오면 출발 자세가 조금씩 달라지고,
출발 자세의 툴 기울기가 곧 CBiRRT 의 구속이기 때문이다.

```bash
$T --goto obs                # 엄격 CBiRRT(구속 유지). free RRT 폴백 없음
$T --goto obs --yes          # 확인 프롬프트 생략
```

실측: hover(J6 +90° 상태)에서 obs 까지 10 waypoints / 2.57 rad, 도착 오차 0.002°.
J6 90° 는 툴축 둘레 회전이라 구속 안에서 그대로 처리된다(§4-1).
이미 그 자리면(최악 관절 0.5° 미만) 아무것도 하지 않는다 -- CBiRRT 는 start==goal
에서도 무작위 트리를 키워 0.58 rad 짜리 왕복을 만들어 실행했었다.

펜던트로 갈 거면 위 컨트롤러 관절값으로 `MovJ`. 돌아온 자리가 맞는지는
`test/vision_target.py --tilt` 가 0.5° 아래인지로 확인한다.
